## What this project is

A learning project, not a production one. The user is a 5th-semester CS student, learning neural networks from first principles. They previously built a working network using plain Python classes (`Neuron`, `Edge`, `Network`) and are now rebuilding it with PyTorch tensors, specifically to learn GPU-friendly, matricized/batched thinking instead of per-object loops. The current task is a toy binary classifier: given `(x, y)`, predict whether the point lies inside a circle (center `(2,1)`, radius `0.4`), trained with a **genetic algorithm** (not backprop/autograd — that's a deliberate choice, see Open items).

## Ground rules — read `learningContract.md` in full

`learningContract.md` is the authoritative, user-maintained contract for how an agent should teach in this project. Summary (do not treat this summary as a substitute for reading the actual file — it gets edited over time):

2. **Let the user explain first, then validate/nudge.** Their learning method is explaining their own understanding back, often self-correcting mid-explanation. Confirm what's right, nudge only the specific gap — don't re-lecture the whole concept, don't pile on caveats they didn't ask for.

4. **Answer length: short.** Small chunks, not essays. Split a long answer across multiple messages rather than one wall of text.
5. **Exceptions to rule 1 require explicit negotiation, not assumption.** When the user asks for a full rewrite of real project code (this has happened once — the initial tensor-port of `training.py`), don't just do it silently. ## Architecture snapshot

**`network.py`**
- `Network` — `@dataclass`: `layers: list[tuple[weights, bias]]` (one tuple per layer, weight shape `[out_features, in_features]`), `loss`, `accuracy` (both `Optional[float]`, set externally after evaluation), `fitness` property (`1/(1+loss)`).
- `forwardPass(inputs)` — batched: `inputs` is `[batch_size, in_features]`, not a single sample. Loops over layers (`ReLU` for all hidden layers), final layer uses `torch.sigmoid` (needed for `crossEntropyLoss` to get a valid probability — the network originally used `ReLU` everywhere, which caused a real, diagnosed failure mode, see Known pitfalls). Matmul form is `outputPrev @ weights.T + bias` (transposed weights, because of the batch dimension — `weights` alone is `[out,in]`, not compatible with a `[batch,in]` input without transposing).
- `batchForwardPass(networks, inputs)` — module-level function (not a `Network` method), runs `forwardPass`'s exact same computation for an entire **population** of `Network`s at once, all sharing one `inputs` batch. Returns `[popSize, batchSize, outputSize]`, deliberately the *same shape convention* as `forwardPass` (just with an extra leading population axis) — don't squeeze/collapse anything inside this function, keep it a pure shape-preserving batched version; any squeezing needed for a specific downstream use (e.g. comparing against `target`) belongs at the call site, not here (see `evaluateNetwork` and the broadcasting entry in Known pitfalls). Mechanics: `inputs.expand(popSize, -1, -1)` gives the shared input a population axis with no copy; per layer, `torch.stack([n.layers[L][0] for n in networks])` stacks that layer's weights across the population (`[popSize,out,in]`), `.transpose(1, 2)` (not `.T` — `.T` reverses *all* axes on a 3D+ tensor, not just the last two) lines it up for matmul, plain `@` already does batched matmul once both operands share a leading population axis (no separate `bmm` call needed), and `popBiases.unsqueeze(1)` reshapes `[popSize,out]` → `[popSize,1,out]` so it broadcasts correctly across the batch axis. Verified bit-identical to looping `forwardPass` per network (smoke-tested, max diff `0.0`).
- `buildNetwork(inputSize, hiddenSizes, outputSize)` — builds layer list. Weight init: `kaiming_uniform_` (ReLU hidden layers), `xavier_uniform_` (sigmoid output layer). Biases: zero-init. All tensors created with `device=DEVICE`.
- `DEVICE` — module-level constant, currently `"cuda:1"` (see Environment/hardware below — index is *not* the same across every environment).

**`training.py`** — problem-agnostic genetic algorithm training engine (no `inCircle`-specific code lives here anymore — see `inCircleNN.py` below). Fully batched across data points (no per-training-point Python loops) *and* fully batched across the population when breeding (see below) — the only remaining Python-level loops are over layer count and a final cheap-indexing unpack, not per-network tensor math.
- `generateTrainingData(criterium, xBounds, yBounds, dataPoints)` → `(pointsTensor [n,2], targetsTensor [n])`. `criterium` is any `(x,y) -> 0.0/1.0` callable — this is what makes the engine swappable across different problems (circle, spiral, etc.), not just circle-specific.
- `crossEntropyLoss(target, prediction)`, `getAccuracy(predictions, target)` — both fully vectorized, both return plain Python `float`s via `.item()` (not tensors — mattered as a recurring bug source; the correct pattern is keeping intermediate values as tensors as long as possible and only converting right before something needs an actual Python number, e.g. string formatting).
- `evaluateNetwork(networks, points, targets)` → `list[Network]` (renamed/rewritten: takes the **whole population** now, not one `Network`). Calls `batchForwardPass` once for everyone, then a cheap per-network loop assigns `.loss`/`.accuracy` directly onto each `Network` object in place and returns the same (mutated) list — no separate per-network `evaluateNetwork` call anywhere in `trainingLoop` anymore. Tensors internally, not floats — see Open items on the `.item()` reduction.
- `crossoverTensor`, `mutateTensor` — elementwise tensor ops (`torch.where`, `torch.rand_like`/`randn_like`) that work unchanged on any shape, which is what makes them reusable for both a single layer and a whole batched-across-children stack.
- `pickRandomParents(selection, size, eliteCount)` → one `[2, size-eliteCount]` index tensor (row 0 = parent-A picks, row 1 = parent-B picks per child), via two `torch.randint` calls + `torch.stack` — no Python loop.
- `breed(selection, parents, sigma, mutationRate)` → `list[Network]`, one per column of `parents`. **Fully batched now** (this was the mid-refactor item, now done): per layer, stacks that layer's weights/biases across all of `selection` (`torch.stack([n.layers[L][0] for n in selection])`), gathers each child's actual parents via fancy-indexing with `parents[0]`/`parents[1]`, runs `crossoverTensor`/`mutateTensor` once on the whole `[numChildren, ...]` stack, then unpacks per-child slices back into individual `Network` objects (a cheap indexing loop, not tensor math).
- `buildPopulation(populationSize, selection, sigma, mutationRate, eliteCount)` — one `pickRandomParents` + one `breed` call produces the `populationSize - eliteCount` bred children, elites are appended straight from `selection` (already sorted best-first).
- `selection(networks, keepPart)` → `list[Network]`, sorted descending by fitness, top `keepPart` fraction. **Rewritten from a Python `sorted(..., key=lambda e: e.fitness)` to `torch.topk`** — the old version was quietly expensive because `e.fitness` is a tensor, and `sorted()` needs a plain bool per comparison to order elements, forcing a GPU→CPU sync on every single comparison during the sort (same underlying cost as the `.item()` lesson, just hiding inside a builtin). New version: stack every network's `.fitness` into one tensor via `torch.stack` (**not** `torch.tensor` — that would force the exact same GPU→CPU copy right back in, since it can't build a tensor from a list of existing tensors without pulling them off the GPU first), then `torch.topk(fTensor, k)` gets the top `k` in one batched GPU op (`sorted=True` by default, so results come back already descending — same as the old sort did). `topk` returns `(values, indices)` — `indices` are positions into the fitness tensor/original list, not `Network` objects, so the last step gathers them back: `[networks[i] for i in sel.indices]` (0-dim index tensors work directly as Python list indices). Verified to select the identical set, in the identical order, as the old `sorted()`-based version, via a dedicated smoke test.
- `trainingLoop` — standard GA loop: evaluate population, keep elites + top `keepPartSelection`, breed+mutate to refill population, repeat for `iterations` generations. Shows a live `tqdm` progress bar (`pip install tqdm` needed per-venv) with the current best network's loss/accuracy as postfix, and reports a per-generation timing breakdown (`EvalTime`/`PopTime`/`SortTime`, renamed from `BestTime`) in its final summary — see Known pitfalls for how all three costs evolved as breeding, evaluation, and now selection each got batched in turn. The single final "best network of the whole run" line is `selection(currPopulation, 1.0)[0]` — don't drop the `[0]` (it happened once, turning `bestNetwork` into the whole population list and crashing on `.loss.item()`), and no need to re-find the max with a second `max(..., key=...)` pass — `selection(..., 1.0)` already returns everyone sorted, so index `0` is already correct.
- No `gpu` constant anymore — imports `DEVICE` directly from `network.py` (single source of truth across all files now; used to be a duplicated constant per file, which caused a real bug — see Known pitfalls).

**`inCircleNN.py`** — the first "problem file": holds `inCircle` (the circle-specific `criterium`), the actual `trainingLoop` calls with real hyperparameters, and `visualize()` — builds a dense `(x,y)` grid (`linspace` + `meshgrid(..., indexing='ij')` + `.flatten()` + `torch.stack(..., dim=1)`), runs it through the trained network's `forwardPass`, reshapes back to a grid, and plots it as a heatmap (`imshow`, needs `.cpu()` before plotting — GPU tensors can't go straight into `matplotlib`) with the true circle overlaid (`plt.Circle`, not computed — drawn directly from known center/radius) for visual comparison. Saves timestamped PNGs to `visualizations/` (`os.makedirs(exist_ok=True)`, filenames via `datetime.now().strftime("%Y-%m-%d_%H-%M-%S")` — replaced an earlier `pngCount`-module-based counter that reset to 0 every fresh run and collided across separate process launches; the old counter also needed an explicit `global` declaration to increment, since `+=` on a variable only assigned inside a function otherwise reads as an uninitialized local — moot now that it's gone, but the general Python rule still applies elsewhere). This is the template for future problem files (e.g. a spiral variant) — same pattern, different `criterium`/bounds/visualization params.

**`proSprudler.py`** — WIP: GA-trains a `[23,23,23]` hidden net (23 inputs, 2 sigmoid outputs `[steer, shoot]`) to play `SprudelJumpEnv` (headless Doodle Jump clone, separate repo `../sprudelJump/env.py`). `sprudlerTrainingLoop` is built and smoke-tested (user wrote it): one `Pool(concInstances, initializer=torch.set_num_threads, initargs=(1,))` around all generations, `p.map(partial(evaluateNetwork, iterations=perNetworkIterations), currGen)` → per-network avg scores, assigned back to `.score` in the main process (workers only get copies), then `SprudlerSelection` (topk, sorted best-first) + `buildPopulation`; returns `selection[0]` (last *evaluated* best, not an unevaluated child). tqdm bar shows best/avg/bestEver score; summary prints avg eval/breed time. Best network is saved at the end via `saveNetwork` → `models/<networkName>_<timestamp>.pt` (dict of `layers` + `score`); `loadNetwork(path)` restores it, e.g. as `startNetwork`. `buildNetwork(..., targetDevice)` param added; `crossoverTensor`/`mutateTensor` now inherit device via `rand_like` instead of forcing `DEVICE`. Local Mac Python (system + `.venv`) is 3.9 — can't import files using `X | None` hints; server `venv-p40` is 3.11. Decisions/findings:
- `env.step()` advances one **frame**, not wall-clock time — no "forward-pass frequency" needed for correctness; action-repeat (call net every k frames) is only an optional speed lever.
- Plan: `multiprocessing.Pool` (not asyncio/threading — CPU-bound, GIL), ~18-20 workers on the server's i9-7900X (10C/20T), forward pass on **CPU** inside each worker (batch-1 GPU calls + `.tolist()` sync per frame would be dispatch-bound), `torch.set_num_threads(1)` per worker. Lockstep/batched-across-games was discussed; user preferred not to. The existing `async` in `runEnv`/`evaluateNetwork` is useless and gets replaced.

- **Server per-frame cost was dominated by torch per-call overhead, not multiprocessing**: measured on the i9 server, batch-1 `forwardPass` = ~109µs (Mac: <13µs) vs `env.step` ~7µs; NumPy was also slow (~56µs), thread/AVX-512 env vars didn't help. ## Environment / hardware — non-obvious, easy to get wrong again

- **Local dev machine has no discrete/CUDA GPU, but `DEVICE` resolves to `"mps"` there, not `"cpu"`** (Apple Silicon's Metal backend counts as available). This matters beyond `forwardPass`/`buildNetwork`: `crossoverTensor`/`mutateTensor` (used by `breed`) also hardcode `device=DEVICE` for their internal random tensors, so any locally-built test `Network` needs its weight/bias tensors created with `device=DEVICE` too (not plain CPU) or you'll hit a `RuntimeError: ... mps:0 and cpu` device mismatch the moment `breed()`/`crossoverTensor` runs on it. Plain-CPU dummy tensors are still fine for testing `forwardPass`/`buildNetwork` in isolation (those don't touch `crossoverTensor`/`mutateTensor`), just not for anything that goes through breeding.
- **Server has two GPUs**: Tesla P40 and GTX 1660. `nvidia-smi`'s own GPU numbering does **not** match PyTorch's `cuda:N` indices in `venv-p40` — `nvidia-smi` labels the P40 as its GPU "0" (PCI-bus-ID order), but PyTorch enumerates fastest-first: **`cuda:0` = GTX 1660, `cuda:1` = Tesla P40**. Confirmed directly via `torch.cuda.get_device_name(0/1)` (not just inferred from `nvidia-smi`'s process table) — this is settled, not a guess. If it's ever in doubt again, re-run that exact check rather than trusting `nvidia-smi`'s display.
- **The GTX 1660 is consistently ~4-6% faster than the Tesla P40 for this workload**, confirmed via matched `hiddenSizes=[4,4]` and `[20]` runs on both (identical hyperparameters, `populationSize=300`, `iterations=1000`) — 1660 beat the P40 on gen/s, total training time, and every one of `EvalTime`/`PopTime`/`BestTime` individually, not just one lucky component. Makes sense architecturally: the 1660 (Turing, 2019) has notably better FP32 throughput than the older P40 (Pascal, 2016), and at this population/batch size the P40's much larger VRAM (23GB vs 6GB) isn't the bottleneck, so raw compute speed wins. Worth re-checking if population size or network size grows large enough that VRAM becomes the constraint instead.
- **Server CPU was stuck at ~0.7-1.2 GHz under full load because of `energy_performance_preference = power`** (governor `powersave`, intel_pstate) — CPU-bound Sprudler training ran at 100% util but low clock and ~41°C. ## Known pitfalls already diagnosed once (don't rediscover from scratch)

- **`ReLU` on the output layer** produces unbounded, non-probability output — broke `crossEntropyLoss` numerically (needed a clamp hack) and, more importantly, caused genuinely flat fitness landscapes (near-zero weights → near-zero pre-activation → `ReLU` output stuck near 0 for everyone → no selection signal → GA just drifts). Fixed via `sigmoid` on the output layer + proper (Kaiming/Xavier) weight init instead of `torch.rand`. Both networks converging to *exactly* `-log(0.5)` or the "always-near-zero" loss value was the diagnostic tell — if loss values look suspiciously like a clean closed-form constant, suspect a degenerate constant-output failure mode, not "just needs more training."
- **Broadcasting silently does the wrong thing**, doesn't error. `[1000]` vs `[1000,1]` combined via `*` broadcasts into a `[1000,1000]` outer-product-like mess instead of pairing elementwise — this happened between `forwardPass`'s output (`[batch,1]`, from `outputSize=1`) and `target` (`[batch]`). Fixed with `.squeeze(1)`. Any time a "loss looks weirdly wrong but doesn't crash," check tensor shapes before logic.
  - **This exact pitfall recurred once already**, when `evaluateNetwork` was rewritten to use `batchForwardPass`: its result is `[popSize, batch, 1]`, so `res[i]` is `[batch, 1]` — still carrying the same trailing `outputSize=1` axis that bit `forwardPass` before. Comparing that against `target` (`[batch]`) in `getAccuracy` broadcast into a `[batch,batch]` grid instead of pairing elementwise, producing accuracy values over 100% (e.g. `10400%`) — a `>100%` or otherwise nonsensical-looking accuracy is the diagnostic tell, same signature as a suspiciously-clean constant loss value elsewhere in this list. Fixed the same way, `.squeeze(-1)`, but note the axis number isn't reusable as a magic constant — it was `1` on the old 2D `[batch,out]` shape, but became `-1` (or `2`) once a population axis got added in front, making `1` mean something else (the batch axis) on the new 3D shape. Always re-derive which axis to squeeze from the *current* shape, don't copy the old axis index.
- **Depth without *enough* width doesn't help — refined from the earlier flat "width beats depth" finding.** `hiddenSizes=[2,2]` performed identically to `hiddenSizes=[2]` (both ~75% accuracy) — width 2 per layer is too narrow a bottleneck for depth to pay off at all. But `hiddenSizes=[3,3]` (width 3 per layer, 6 total neurons) *slightly beat* `hiddenSizes=[5]` (~98.7% vs ~97.2%) — once each layer clears some minimum width, depth does start to help. `hiddenSizes=[10]` performed about the same as `[3,3]` (~98.3-98.7%) — this problem's accuracy ceiling seems to sit around 98-99% regardless of further capacity increases past that point; more neurons stopped mattering once both configs cleared the real bottleneck.
- **A single hidden layer of N ReLU neurons (feeding one sigmoid output) draws a decision boundary that's a convex polygon with *at most N sides*** — one straight edge per hidden neuron, visually confirmed (`hiddenSizes=[5]` produced a visibly pentagon-ish boundary in `visualize()`'s output). This is a real, known property of single-hidden-layer ReLU networks, not a coincidence — worth remembering when explaining *why* a given architecture's decision boundary looks the way it does. It does **not** extend cleanly to multi-layer networks (a second layer combines the first layer's already-bent outputs in more complex, potentially non-convex ways) — don't apply the same "N neurons = N-gon" counting once there's more than one hidden layer.
- **All three per-generation costs (breeding, evaluation, selection) are now fully batched — `EvalTime` is back in a clear, wide lead, at roughly 5x either of the other two.** Full progression on P40, `[4,4]`/`[20]`, `populationSize=300`, `iterations=1000`:
  | stage | PopTime | EvalTime | Sort/BestTime | gen/s |
  |---|---|---|---|---|
  | pre-refactor | ~0.18-0.27s | (not yet dominant) | ~0.06-0.07s | ~4.6-4.9 |
  | breeding batched | ~0.01s | ~0.12-0.14s | ~0.06-0.07s | ~4.6-5.4 (eval now dominant) |
  | + eval batched | ~0.010-0.014s | ~0.073-0.074s | ~0.067s (tied w/ eval) | ~6.4-6.75 |
  | + selection batched (`topk`) | ~0.010-0.016s | ~0.073-0.075s | ~0.014-0.016s | ~9.4-10.1 |

  Net effect across the whole session: roughly **4s/iteration down to ~0.1s/iteration**, a ~40x speedup, purely from replacing per-network Python loops with population-batched tensor ops at each of the three stages in turn — each fix correctly predicted the *next* bottleneck before touching it. `EvalTime` is now the only cost worth optimizing further if chasing more raw speed for a single run.
- **GPU utilization during training is only ~15-20% on the P40**, even with everything now batched — this workload is dispatch/kernel-launch-bound at this population/data size, not compute-bound. Means there's real spare capacity for running more work concurrently (e.g. multiple independent `trainingLoop`s testing different hyperparameters) without meaningfully slowing any individual run down — see the parallel-runs open item below, now with actual evidence it's worth doing.
  - **Confirmed directly: much bigger architectures cost almost nothing, up to a point — then the trend reverses hard.** `[4,4]` → `[7,4]` → `[30,15]` (8 → 11 → 45 total neurons) all measured `EvalTime` ~0.073-0.075s/gen, genuinely flat. `[200]` (single layer, 10x wider than `[20]`) broke the pattern modestly: `EvalTime` ~0.088s/gen (~20% up), gen/s 8.75 vs ~9.4-10.1 baseline. Pushed much further, the trend accelerates sharply: `[100,100,50,25]` (4 layers, modest per-layer widths ≤100) → `EvalTime` 0.115s/gen, ~6.35gen/s; `[750,500]` (only 2 layers, but very wide) → `EvalTime` **0.360s/gen**, gen/s crashed to 2.34 — over 3x Network #1's own `EvalTime` in the same session despite *half* the layer count. Interpretation: this marks the actual crossover from dispatch-bound to compute-bound. At small widths, *layer count* dominated cost (more kernel launches, each cheap) — that's the older "PopTime scales with layer count not neuron count" finding. Once per-layer width gets large enough (hundreds+), *width* dominates instead (fewer launches, but each one now doing real FLOPs) — `PopTime` shows the same reversal, `[750,500]` (2 layers) costing more (0.053s) than `[100,100,50,25]` (4 layers, 0.026s) specifically because `breed()`'s elementwise ops are now expensive in their own right, not just dispatch overhead. Don't extrapolate the "layer count over width" rule past small architectures — it flips once individual layers get wide enough.
  - **Memory, separately from speed: `batchForwardPass` materializes one activation tensor of shape `[popSize, dataPoints, hiddenWidth]` per layer, unbounded.** For `hiddenSizes=[2000,1000]`, `populationSize=300`, `dataPoints=5000`: `300 × 5000 × 2000 × 4 bytes ≈ 11.2 GiB` for just that one intermediate — caused a real `CUDA out of memory` crash on the P40 (22GB) once another process was also resident. A chunked-forward-pass fix (process `dataPoints` in chunks, bounding peak memory to `popSize × chunkSize × hiddenWidth` instead) was prototyped and verified correct (`torch.allclose` against the unchunked version passed) but **not kept** — risked adding ~10x more kernel launches per generation for architectures that never needed chunking in the first place, which is exactly the dispatch overhead this session spent most of its effort eliminating; reverted in favor of just testing smaller architectures (`[750,500]` instead of `[2000,1000]`) for now. If testing architectures this wide becomes a regular need, revisit chunking, but make it conditional (only chunk when the estimated activation size actually warrants it) rather than always-on.
  - **Very wide/deep GA-trained networks (`[100,100,50,25]`, `[750,500]`) underperform smaller ones on accuracy at the same generation budget — turns out to be a genuine plateau, not just slow convergence.** `[750,500]` at `iterations=1000/5000/15000`: 71.00% → 80.78% → **80.76%**. Real improvement happened between 1000 and 5000 gens, then completely flatlined for another 3x the generations (~72 more minutes of wall-clock training bought nothing) — so this isn't "still climbing, just slowly," it's stuck at a local optimum around ~80-81% for this specific architecture/hyperparameter combination. Leading hypothesis, not yet tested: `sigma`/`mutationRate` were tuned against much smaller architectures, and the same absolute mutation step size is likely far too small relative to a `[750,500]` network's much larger parameter space to escape a local optimum once near one — worth trying a larger `sigma` specifically on this architecture before concluding ~80% is a hard ceiling. Smaller architectures (`[100,100,50,25]` → 74.60% at 1000 gens, not yet re-tested at higher iteration counts) may or may not show the same plateau pattern. Underlying cause either way: a genetic algorithm searches parameter space via essentially-random crossover/mutation, which scales far worse with dimensionality than gradient descent's directional search — a concrete, empirically-confirmed illustration of why this project's original choice to use a GA instead of backprop (see "What this project is") is a real tradeoff, and why real large models use gradient-based methods instead of population-based search.
- **`hiddenSizes=[4,4]` shows large run-to-run accuracy variance — don't trust a single run for a borderline-width architecture.** Two runs with identical hyperparameters (`populationSize=300`, `iterations=1000`, no fixed seed) landed at 73.82% and 97.64% accuracy — a ~24-point swing from the exact same config, just different random init/crossover/mutation trajectories. Compare to `hiddenSizes=[20]`, which landed within half a point (98.52% vs 98.24%) across the same two runs. Fits the earlier finding that `[2,2]` is too narrow and `[3,3]` reliably clears the bottleneck — `[4,4]` looks like it sits right on that edge, sometimes converging well and sometimes getting stuck. Don't judge a narrow/borderline architecture's accuracy from one run; either average multiple runs or fix a seed before comparing architectures head-to-head.
- **Breeding cost (`PopTime`) scales with layer *count*, not total neuron count.** `hiddenSizes=[3,3]` (2 layers) has a noticeably higher `PopTime` (~0.27s/gen) than `hiddenSizes=[10]` (1 layer, ~0.18s/gen), despite similar total neurons — `breed()` loops once per layer doing 4 tensor ops each, so more layers directly means more of those per child. Relevant to both architecture choices and to the in-progress breeding-batching work below.
- **Two separate device constants (`network.py`'s `DEVICE`, `training.py`'s old `gpu`) caused a real crash** when only one got updated to auto-detect CPU/MPS/CUDA — running on a CUDA-less Mac crashed inside `training.py` because its `gpu` constant was still hardcoded to `"cuda:1"`. Fixed by having `training.py` import `DEVICE` from `network.py` instead of keeping its own copy — one source of truth. If a third file/module ever needs the device, import `DEVICE` from `network.py`, don't redeclare it.

- **`breed()`'s per-generation stack+index pattern causes real CUDA memory fragmentation on large networks, building up gradually across generations rather than crashing immediately.** Discovered while training `frogDetector.py` (a new problem file, CIFAR-10 frog-vs-rest binary classification, dense/GA — not convolutional, deliberately, to feel the mismatch between a fully-connected architecture and image input). Two distinct OOM causes found, not one:
  1. **Population-at-rest memory, hit immediately (generation 0-2).** Unlike the earlier activation-memory OOM (scales with `dataPoints`), this one scales with `populationSize × totalParameterCount`. A `hiddenSizesHunter=[2000,1000,750,500,250,100,50,10]` network (~9.4M params, dominated by the `3072→2000` first layer) at `populationSize=200` needs ~7.5GB just to hold the population's weights at rest — and `breed()` needs the old population alive *while* building an entirely new one via `torch.stack`/fancy-indexing (which copies, not views), so peak is roughly double that plus per-layer transients. Fixed for this case by dropping `populationSize` to `50`.
  2. **Fragmentation, building up gradually within a single run, even after (1) is fixed.** At `populationSize=50`, `hiddenSizesHunter` (~9.4M params) trained cleanly for a full 500 generations. `hiddenSizesLover` ([2500,2000,2000,500,250,50], ~17.8M params, same `populationSize=50`) crashed **at generation 79**, not immediately — `torch.cuda.empty_cache()` between the two `trainingLoop` calls pushed the crash from generation 2 to generation 79, i.e. helped but didn't fix it. Per-generation memory demand should be constant (same tensor shapes every generation), so a crash after 79 successful generations, with `reserved but unallocated` memory visibly growing (5.81 GiB at crash time), points at the allocator failing to reuse previously-freed blocks across generations (many differently-shaped per-layer tensors each generation), not a Python-level reference leak. PyTorch's own OOM message suggests `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` — not yet confirmed whether this actually resolves it for `hiddenSizesLover`, next thing to test.
  - **Practical implication**: for any network this large under this GA engine, expect two separate memory ceilings to check, not one — "does it fit for one generation" and "does memory stay stable across hundreds of generations." A run surviving its first several generations is not proof it'll survive the whole thing.

- **The accuracy-over-generations plot (finally built) reveals GA improvement is a staircase, not a curve — long flat stretches punctuated by sudden jumps, not gradual climbing.** First real per-generation trace (`hiddenSizesLover=[256,256,256,256,256]` ≈1.05M params, `populationSize=25`, 1000 iterations, 32s total — `frogDetector.py`'s new `accuracyLog`, returned from `trainingLoop` alongside `bestNetwork`). Shape: flat at ~54.9% for ~150-180 generations, then three rapid jumps (→61%→62.5%→64.65%), then **completely flat for the remaining ~800 generations (80% of the run)**. This is structurally a staircase because the plotted value is the *elite's* accuracy — elitism means the best individual always survives into the next generation, so the line can only go up or stay flat, never down; a flat stretch means no child beat the current record that generation, not that nothing was being tried. Directly explains why widely-spaced snapshots (e.g. the `[750,500]` 1000/5000/15000-iteration data) looked like a clean plateau — the real dynamics are lucky-jump-then-stall, and most of a long run's generations can be pure waiting. Motivates the next untested lever concretely: a bigger `populationSize` means more independent mutation attempts per generation, which should shorten the flat "waiting for a lucky jump" stretches, not just abstractly "search more."
  - **Confirmed at 10x and then 100x the generation count, same `populationSize=25` throughout (verified from the printed summary each time — an earlier claim of "popSize 500" for the 100k run was checked and was wrong, it was still 25)**: 1,000 iterations → 64.65%, 10,000 iterations → 66.55%, 100,000 iterations → 66.75%. Going from 10k to 100k (10x more generations, ~54 minutes) bought only +0.2 points — about as conclusive a plateau confirmation as this project has produced. `hiddenSizesLover=[256,256,256,256,256]` at `populationSize=25` has a real, hard ceiling around ~65-67% for this task. `populationSize=500` (the ~6x-VRAM-multiplier-calculated headroom, meant to test whether more diversity per generation shortens the flat stretches) still has not actually been run as of this note — genuinely the next open test, not yet confirmed either way (attempted twice, both times the printed summary showed `populationSize=25` again, so the config change hadn't actually been made either time).
  - **Run-to-run variance at 100k iterations, `populationSize=25`, same config**: 66.75% (loss 0.6147) vs. 68.40% (loss 0.6096) across two separate runs, no fixed seed — ~1.7 points apart from nothing but random init/mutation differences. Consistent with the earlier `[4,4]` finding: don't over-read a single run's exact number for a borderline-capacity architecture, there's real spread.
- **A network many times smaller than `hiddenSizesHunter`/`hiddenSizesLover`'s original giant sizes recovered `SortTime` back to its normal cheap range.** `[256,256,256,256,256]` (~1.05M params) at `populationSize=25`: `SortTime` was `0.013s` — back in line with the original small-toy-problem numbers, not the mysterious `~0.75s` that dominated every run on the 9-18M-param networks. Good evidence that the earlier `SortTime` anomaly (flagged as unexplained) really was a side effect of running close to the VRAM ceiling on those huge networks (allocator overhead spilling into whichever operation happened to sync next), not a real regression in `selection()`'s `topk` implementation.
- **VRAM estimation for a new architecture/population size**: naive "population size × per-network param count" badly underestimates peak usage — `breed()`'s per-layer `stack`+fancy-index pattern needs several full population-sized copies alive at once. Empirically, peak usage has run **roughly 6x** the population's at-rest weight memory across the sizes tested so far (calibrated from FrogLover's real OOM: ~17.8M params × `populationSize=50` was only ~3.56GB at rest but peaked around ~20-22GB). Use that ~6x multiplier as a rule of thumb for any new size/population combination before committing to a long run, not just the raw at-rest figure.

## Open items discussed but not yet done

- **Breeding-batching refactor is DONE** and smoke-tested. `breed()` and `buildPopulation()` are fully rewritten: `breed(selection, parents, sigma, mutationRate)` stacks each layer's weights/biases across `selection`, gathers per-child parents via fancy-indexing with `parents[0]`/`parents[1]`, runs `crossoverTensor`/`mutateTensor` once per layer on the whole batch, then unpacks into individual `Network` objects. `buildPopulation` calls `pickRandomParents` + `breed` once each, no more per-child loop.
- **Evaluation-batching refactor is also DONE** and smoke-tested (both against `forwardPass` for exact-match correctness, and end-to-end via a real `trainingLoop` run). New `batchForwardPass(networks, inputs)` in `network.py` runs every network in the population through one batched matmul chain instead of looping `forwardPass` per network; `evaluateNetwork` calls it once and mutates `.loss`/`.accuracy` onto each `Network` in place. See the `training.py`/`network.py` sections under Architecture snapshot for the current (correct) shape of all of this, and Known pitfalls for a broadcasting bug this refactor reintroduced and how it was caught.
  - **Next natural follow-up, not yet done:** `selection`'s Python `sorted()` call is now the only one of the three per-generation costs (`EvalTime`/`PopTime`/`BestTime`) still doing unbatched per-network work — see the timing breakdown in Known pitfalls. Worth investigating whether it can be vectorized (e.g. `torch.argsort` on a tensor of fitness values instead of a Python-level `sorted` with a lambda key) now that it's tied for the biggest remaining cost.
- **The `.item()`-reduction optimization's actual effect is unresolved/ambiguous — don't assume it was a clean win.** Removing most `.item()` calls (keeping `loss`/`accuracy` as tensors through the population loop, converting only at the `tqdm` postfix and final summary) was expected to speed things up by cutting GPU↔CPU sync points. One measured comparison afterward showed it running *slower* (`1.73gen/s` vs an earlier `2.67gen/s` baseline) — not explained, possibly noise/early-iteration measurement, possibly something real about async GPU work in this pattern. Worth actually investigating (e.g. controlled before/after comparison) before assuming this change was purely beneficial.
- **No train/test split exists yet.** All accuracy/loss numbers so far are in-sample (evaluated on the same data trained on). Still the highest-priority correctness item before trusting any of the accuracy numbers as "generalizes well" — current ~98% numbers are all in-sample.
- **Running multiple independent `trainingLoop` calls in parallel** (e.g. testing several `hiddenSizes` configs at once) — now backed by real evidence it's worth doing: GPU utilization sits at only ~15-20% on the P40 even with breeding/eval/selection all batched, so there's genuine spare capacity, not just a theoretical argument. Two approaches discussed, recommend starting with (a) given the effort gap: (a) genuinely simplest — just launch `python3 inCircleNN.py` from separate terminals/processes independently (no `fork`-after-CUDA-init problem at all this way, since each is a fresh process, and no code changes needed) — the hardcoded hyperparameters still need varying between copies, but the filename-collision issue is now fixed (`visualize()` names PNGs by timestamp, not a per-run-reset counter, so concurrent/separate runs no longer overwrite each other); (b) a proper `multiprocessing`/`ProcessPoolExecutor` wrapper with the **`'spawn'` start method** (not `'fork'`) if launching from within one Python script, or a deeper refactor adding a *second* batch dimension (on top of the population one) across `breed`/`evaluateNetwork`/`selection` so one process handles several populations simultaneously — either could push a single conceptual experiment's wall-clock time down further, at meaningfully more implementation cost than (a). Neither (b) built yet. VRAM is a real constraint on the 1660 (6GB) for many concurrent processes — the P40 (23GB) is the better target.
- CUDA streams (overlap population members' evaluation without a full population-batching rewrite) — mentioned early on as a smaller intermediate option to breeding/evaluation batching; moot now that both are actually batched instead.
- Next architecture worth testing, now that a spiral/other-problem file is planned: a genuinely harder 2D problem (spiral was the discussed candidate, chosen specifically because small networks reliably fail it) — would need a new problem file (e.g. `spiralNN.py`) following `inCircleNN.py`'s pattern.
- **A fitness/accuracy-over-generations line plot was requested but not yet built.** Needs: (1) `trainingLoop` recording the best network's loss/accuracy every generation into a list (currently computed for the `tqdm` postfix each iteration but discarded, not retained), (2) a new plotting function (line plot, not heatmap — x = generation, y = accuracy/loss, one line per architecture) to compare e.g. `[2,2]` vs `[5]` vs `[3,3]` vs `[10]`'s learning curves directly.
