# AGENTS.md — tensorNetwork

Read this file (and `learningContract.md`, which it summarizes) at the start of every session on this repo. Keep both up to date — see "Keeping this file current" at the bottom.

## What this project is

A learning project, not a production one. The user is a 5th-semester CS student, learning neural networks from first principles. They previously built a working network using plain Python classes (`Neuron`, `Edge`, `Network`) and are now rebuilding it with PyTorch tensors, specifically to learn GPU-friendly, matricized/batched thinking instead of per-object loops. The current task is a toy binary classifier: given `(x, y)`, predict whether the point lies inside a circle (center `(2,1)`, radius `0.4`), trained with a **genetic algorithm** (not backprop/autograd — that's a deliberate choice, see Open items).

## Ground rules — read `learningContract.md` in full

`learningContract.md` is the authoritative, user-maintained contract for how an agent should teach in this project. Summary (do not treat this summary as a substitute for reading the actual file — it gets edited over time):

1. **Teach transfer, don't hand over code.** For the user's actual project code (`network.py`/`training.py`), don't give copy-paste-ready fixes. Point at the concept (often via an unrelated analogy — cars, recipes, etc.), let the user write the actual line.
2. **Let the user explain first, then validate/nudge.** Their learning method is explaining their own understanding back, often self-correcting mid-explanation. Confirm what's right, nudge only the specific gap — don't re-lecture the whole concept, don't pile on caveats they didn't ask for.
3. **What's fine to do directly (no analogy needed):** pointing out *that* something is a bug and *why*, conceptually; explaining language/library rules, APIs, and conventions directly (e.g. what `.squeeze()` does, what `torch.rand` returns); fully worked examples when explicitly requested outside a "fix my code" context; purely mechanical, non-learning-bearing edits (e.g. a find-and-replace refactor, once the user understands *why*) — use judgment, but default to teaching over doing.
4. **Answer length: short.** Small chunks, not essays. Split a long answer across multiple messages rather than one wall of text.
5. **Exceptions to rule 1 require explicit negotiation, not assumption.** When the user asks for a full rewrite of real project code (this has happened once — the initial tensor-port of `training.py`), don't just do it silently. Surface the tension against the contract and ask (e.g. via a clarifying question) whether they want a one-time exception, heavier scaffolding instead, or a standing contract change. One granted exception does not imply standing permission for future asks.

If the user gives new teaching-style feedback mid-conversation ("I don't want X", "do more of Y"), update `learningContract.md` to capture it — don't just apply it silently for the rest of the session and forget it next time.

## Architecture snapshot

**`network.py`**
- `Network` — `@dataclass`: `layers: list[tuple[weights, bias]]` (one tuple per layer, weight shape `[out_features, in_features]`), `loss`, `accuracy` (both `Optional[float]`, set externally after evaluation), `fitness` property (`1/(1+loss)`).
- `forwardPass(inputs)` — batched: `inputs` is `[batch_size, in_features]`, not a single sample. Loops over layers (`ReLU` for all hidden layers), final layer uses `torch.sigmoid` (needed for `crossEntropyLoss` to get a valid probability — the network originally used `ReLU` everywhere, which caused a real, diagnosed failure mode, see Known pitfalls). Matmul form is `outputPrev @ weights.T + bias` (transposed weights, because of the batch dimension — `weights` alone is `[out,in]`, not compatible with a `[batch,in]` input without transposing).
- `buildNetwork(inputSize, hiddenSizes, outputSize)` — builds layer list. Weight init: `kaiming_uniform_` (ReLU hidden layers), `xavier_uniform_` (sigmoid output layer). Biases: zero-init. All tensors created with `device=DEVICE`.
- `DEVICE` — module-level constant, currently `"cuda:1"` (see Environment/hardware below — index is *not* the same across every environment).

**`training.py`** — problem-agnostic genetic algorithm training engine (no `inCircle`-specific code lives here anymore — see `inCircleNN.py` below). Fully batched across data points (no per-training-point Python loops) *and* fully batched across the population when breeding (see below) — the only remaining Python-level loops are over layer count and a final cheap-indexing unpack, not per-network tensor math.
- `generateTrainingData(criterium, xBounds, yBounds, dataPoints)` → `(pointsTensor [n,2], targetsTensor [n])`. `criterium` is any `(x,y) -> 0.0/1.0` callable — this is what makes the engine swappable across different problems (circle, spiral, etc.), not just circle-specific.
- `crossEntropyLoss(target, prediction)`, `getAccuracy(predictions, target)` — both fully vectorized, both return plain Python `float`s via `.item()` (not tensors — mattered as a recurring bug source; the correct pattern is keeping intermediate values as tensors as long as possible and only converting right before something needs an actual Python number, e.g. string formatting).
- `evaluateNetwork(network, points, targets)` → `(loss, accuracy)` (tensors internally now, not floats — see Open items on the `.item()` reduction).
- `crossoverTensor`, `mutateTensor` — elementwise tensor ops (`torch.where`, `torch.rand_like`/`randn_like`) that work unchanged on any shape, which is what makes them reusable for both a single layer and a whole batched-across-children stack.
- `pickRandomParents(selection, size, eliteCount)` → one `[2, size-eliteCount]` index tensor (row 0 = parent-A picks, row 1 = parent-B picks per child), via two `torch.randint` calls + `torch.stack` — no Python loop.
- `breed(selection, parents, sigma, mutationRate)` → `list[Network]`, one per column of `parents`. **Fully batched now** (this was the mid-refactor item, now done): per layer, stacks that layer's weights/biases across all of `selection` (`torch.stack([n.layers[L][0] for n in selection])`), gathers each child's actual parents via fancy-indexing with `parents[0]`/`parents[1]`, runs `crossoverTensor`/`mutateTensor` once on the whole `[numChildren, ...]` stack, then unpacks per-child slices back into individual `Network` objects (a cheap indexing loop, not tensor math).
- `buildPopulation(populationSize, selection, sigma, mutationRate, eliteCount)` — one `pickRandomParents` + one `breed` call produces the `populationSize - eliteCount` bred children, elites are appended straight from `selection` (already sorted best-first).
- `selection`, `trainingLoop` — standard GA loop: evaluate population, keep elites + top `keepPartSelection`, breed+mutate to refill population, repeat for `iterations` generations. `trainingLoop` shows a live `tqdm` progress bar (`pip install tqdm` needed per-venv) with the current best network's loss/accuracy as postfix, and reports a per-generation timing breakdown (`EvalTime`/`PopTime`/`BestTime`) in its final summary — see Known pitfalls, `PopTime` (breeding) *was* the biggest per-generation cost pre-refactor; worth re-profiling now that breeding is batched to see whether that's still true.
- No `gpu` constant anymore — imports `DEVICE` directly from `network.py` (single source of truth across all files now; used to be a duplicated constant per file, which caused a real bug — see Known pitfalls).

**`inCircleNN.py`** — the first "problem file": holds `inCircle` (the circle-specific `criterium`), the actual `trainingLoop` calls with real hyperparameters, and `visualize()` — builds a dense `(x,y)` grid (`linspace` + `meshgrid(..., indexing='ij')` + `.flatten()` + `torch.stack(..., dim=1)`), runs it through the trained network's `forwardPass`, reshapes back to a grid, and plots it as a heatmap (`imshow`, needs `.cpu()` before plotting — GPU tensors can't go straight into `matplotlib`) with the true circle overlaid (`plt.Circle`, not computed — drawn directly from known center/radius) for visual comparison. Saves timestamped PNGs to `visualizations/` (`os.makedirs(exist_ok=True)`, filenames via `datetime.now().strftime("%Y-%m-%d_%H-%M-%S")` — replaced an earlier `pngCount`-module-based counter that reset to 0 every fresh run and collided across separate process launches; the old counter also needed an explicit `global` declaration to increment, since `+=` on a variable only assigned inside a function otherwise reads as an uninitialized local — moot now that it's gone, but the general Python rule still applies elsewhere). This is the template for future problem files (e.g. a spiral variant) — same pattern, different `criterium`/bounds/visualization params.

## Environment / hardware — non-obvious, easy to get wrong again

- **Local dev machine has no discrete/CUDA GPU, but `DEVICE` resolves to `"mps"` there, not `"cpu"`** (Apple Silicon's Metal backend counts as available). This matters beyond `forwardPass`/`buildNetwork`: `crossoverTensor`/`mutateTensor` (used by `breed`) also hardcode `device=DEVICE` for their internal random tensors, so any locally-built test `Network` needs its weight/bias tensors created with `device=DEVICE` too (not plain CPU) or you'll hit a `RuntimeError: ... mps:0 and cpu` device mismatch the moment `breed()`/`crossoverTensor` runs on it. Plain-CPU dummy tensors are still fine for testing `forwardPass`/`buildNetwork` in isolation (those don't touch `crossoverTensor`/`mutateTensor`), just not for anything that goes through breeding.
- **Server has two GPUs**: Tesla P40 and GTX 1660. `nvidia-smi`'s own GPU numbering does **not** match PyTorch's `cuda:N` indices in `venv-p40` — `nvidia-smi` labels the P40 as its GPU "0" (PCI-bus-ID order), but PyTorch enumerates fastest-first: **`cuda:0` = GTX 1660, `cuda:1` = Tesla P40**. Confirmed directly via `torch.cuda.get_device_name(0/1)` (not just inferred from `nvidia-smi`'s process table) — this is settled, not a guess. If it's ever in doubt again, re-run that exact check rather than trusting `nvidia-smi`'s display.
- **The GTX 1660 is consistently ~4-6% faster than the Tesla P40 for this workload**, confirmed via matched `hiddenSizes=[4,4]` and `[20]` runs on both (identical hyperparameters, `populationSize=300`, `iterations=1000`) — 1660 beat the P40 on gen/s, total training time, and every one of `EvalTime`/`PopTime`/`BestTime` individually, not just one lucky component. Makes sense architecturally: the 1660 (Turing, 2019) has notably better FP32 throughput than the older P40 (Pascal, 2016), and at this population/batch size the P40's much larger VRAM (23GB vs 6GB) isn't the bottleneck, so raw compute speed wins. Worth re-checking if population size or network size grows large enough that VRAM becomes the constraint instead.
- **`venv-p40`** (Python 3.11, `uv`, `torch==2.4.1+cu121`) is the environment that actually supports the P40 — its Pascal architecture (`sm_61`) was dropped from newer official PyTorch builds, so this specific torch version is a hard requirement, not a preference. Shell aliases `tnvenv`/`tnp40` jump into the project and activate the right venv (`tnp40` = P40/CUDA env, `tnvenv` = the other one).
- **The GTX 1660 can be passed through to a Windows VM** (`vmstart`/`vmstop` aliases in `.zshrc`). If that VM is running, the 1660 (and whatever CUDA index it held) becomes invisible to the training process — device indices can shift as a result. Don't assume `cuda:1` is stable across sessions without checking.

## Known pitfalls already diagnosed once (don't rediscover from scratch)

- **`ReLU` on the output layer** produces unbounded, non-probability output — broke `crossEntropyLoss` numerically (needed a clamp hack) and, more importantly, caused genuinely flat fitness landscapes (near-zero weights → near-zero pre-activation → `ReLU` output stuck near 0 for everyone → no selection signal → GA just drifts). Fixed via `sigmoid` on the output layer + proper (Kaiming/Xavier) weight init instead of `torch.rand`. Both networks converging to *exactly* `-log(0.5)` or the "always-near-zero" loss value was the diagnostic tell — if loss values look suspiciously like a clean closed-form constant, suspect a degenerate constant-output failure mode, not "just needs more training."
- **Broadcasting silently does the wrong thing**, doesn't error. `[1000]` vs `[1000,1]` combined via `*` broadcasts into a `[1000,1000]` outer-product-like mess instead of pairing elementwise — this happened between `forwardPass`'s output (`[batch,1]`, from `outputSize=1`) and `target` (`[batch]`). Fixed with `.squeeze(1)`. Any time a "loss looks weirdly wrong but doesn't crash," check tensor shapes before logic.
- **Depth without *enough* width doesn't help — refined from the earlier flat "width beats depth" finding.** `hiddenSizes=[2,2]` performed identically to `hiddenSizes=[2]` (both ~75% accuracy) — width 2 per layer is too narrow a bottleneck for depth to pay off at all. But `hiddenSizes=[3,3]` (width 3 per layer, 6 total neurons) *slightly beat* `hiddenSizes=[5]` (~98.7% vs ~97.2%) — once each layer clears some minimum width, depth does start to help. `hiddenSizes=[10]` performed about the same as `[3,3]` (~98.3-98.7%) — this problem's accuracy ceiling seems to sit around 98-99% regardless of further capacity increases past that point; more neurons stopped mattering once both configs cleared the real bottleneck.
- **A single hidden layer of N ReLU neurons (feeding one sigmoid output) draws a decision boundary that's a convex polygon with *at most N sides*** — one straight edge per hidden neuron, visually confirmed (`hiddenSizes=[5]` produced a visibly pentagon-ish boundary in `visualize()`'s output). This is a real, known property of single-hidden-layer ReLU networks, not a coincidence — worth remembering when explaining *why* a given architecture's decision boundary looks the way it does. It does **not** extend cleanly to multi-layer networks (a second layer combines the first layer's already-bent outputs in more complex, potentially non-convex ways) — don't apply the same "N neurons = N-gon" counting once there's more than one hidden layer.
- **Post-refactor, breeding is no longer the bottleneck — `PopTime` dropped to ~0.01s/gen** (from ~0.18-0.27s/gen pre-refactor, see the layer-count-scaling finding below), confirmed on real server runs (`[4,4]` and `[20]`, both GPUs). `EvalTime` (~0.12-0.14s/gen) is now clearly dominant, and `BestTime` (selection/sorting, ~0.06-0.07s/gen) — previously negligible next to breeding — is now the *second*-largest cost. If chasing more speed, evaluation or selection are the next targets, not breeding.
- **`hiddenSizes=[4,4]` shows large run-to-run accuracy variance — don't trust a single run for a borderline-width architecture.** Two runs with identical hyperparameters (`populationSize=300`, `iterations=1000`, no fixed seed) landed at 73.82% and 97.64% accuracy — a ~24-point swing from the exact same config, just different random init/crossover/mutation trajectories. Compare to `hiddenSizes=[20]`, which landed within half a point (98.52% vs 98.24%) across the same two runs. Fits the earlier finding that `[2,2]` is too narrow and `[3,3]` reliably clears the bottleneck — `[4,4]` looks like it sits right on that edge, sometimes converging well and sometimes getting stuck. Don't judge a narrow/borderline architecture's accuracy from one run; either average multiple runs or fix a seed before comparing architectures head-to-head.
- **Breeding cost (`PopTime`) scales with layer *count*, not total neuron count.** `hiddenSizes=[3,3]` (2 layers) has a noticeably higher `PopTime` (~0.27s/gen) than `hiddenSizes=[10]` (1 layer, ~0.18s/gen), despite similar total neurons — `breed()` loops once per layer doing 4 tensor ops each, so more layers directly means more of those per child. Relevant to both architecture choices and to the in-progress breeding-batching work below.
- **Two separate device constants (`network.py`'s `DEVICE`, `training.py`'s old `gpu`) caused a real crash** when only one got updated to auto-detect CPU/MPS/CUDA — running on a CUDA-less Mac crashed inside `training.py` because its `gpu` constant was still hardcoded to `"cuda:1"`. Fixed by having `training.py` import `DEVICE` from `network.py` instead of keeping its own copy — one source of truth. If a third file/module ever needs the device, import `DEVICE` from `network.py`, don't redeclare it.

## Open items discussed but not yet done

- **Breeding-batching refactor is DONE** (was IN PROGRESS as of the last update to this file — now complete and smoke-tested). `breed()` and `buildPopulation()` are fully rewritten per the plan that used to live here: `breed(selection, parents, sigma, mutationRate)` stacks each layer's weights/biases across `selection`, gathers per-child parents via fancy-indexing with `parents[0]`/`parents[1]`, runs `crossoverTensor`/`mutateTensor` once per layer on the whole batch, then unpacks into individual `Network` objects. `buildPopulation` calls `pickRandomParents` + `breed` once each, no more per-child loop. See the `training.py` section under Architecture snapshot for the current (correct) shape of all of this.
  - **Next natural follow-up, not yet done:** re-profile (`EvalTime`/`PopTime`/`BestTime`) on the server now that breeding is batched, to see whether `PopTime` is still the dominant per-generation cost or whether evaluation is now the bottleneck again.
- **The `.item()`-reduction optimization's actual effect is unresolved/ambiguous — don't assume it was a clean win.** Removing most `.item()` calls (keeping `loss`/`accuracy` as tensors through the population loop, converting only at the `tqdm` postfix and final summary) was expected to speed things up by cutting GPU↔CPU sync points. One measured comparison afterward showed it running *slower* (`1.73gen/s` vs an earlier `2.67gen/s` baseline) — not explained, possibly noise/early-iteration measurement, possibly something real about async GPU work in this pattern. Worth actually investigating (e.g. controlled before/after comparison) before assuming this change was purely beneficial.
- **No train/test split exists yet.** All accuracy/loss numbers so far are in-sample (evaluated on the same data trained on). Still the highest-priority correctness item before trusting any of the accuracy numbers as "generalizes well" — current ~98% numbers are all in-sample.
- **Running multiple independent `trainingLoop` calls in parallel** (e.g. testing several `hiddenSizes` configs at once) — two approaches discussed: (a) genuinely simplest — just launch `python3 inCircleNN.py` from separate terminals/processes independently (no `fork`-after-CUDA-init problem at all this way, since each is a fresh process) — the hardcoded hyperparameters still need varying between copies, but the filename-collision issue is now fixed (`visualize()` names PNGs by timestamp, not a per-run-reset counter, so concurrent/separate runs no longer overwrite each other); (b) a proper `multiprocessing`/`ProcessPoolExecutor` wrapper with the **`'spawn'` start method** (not `'fork'`) if launching from within one Python script. Neither built yet. VRAM is a real constraint on the 1660 (6GB) for many concurrent processes — the P40 (23GB) is the better target.
- CUDA streams (overlap population members' evaluation without a full population-batching rewrite) — mentioned as a smaller intermediate option, not pursued since profiling showed breeding, not evaluation, is now the bigger cost.
- Next architecture worth testing, now that a spiral/other-problem file is planned: a genuinely harder 2D problem (spiral was the discussed candidate, chosen specifically because small networks reliably fail it) — would need a new problem file (e.g. `spiralNN.py`) following `inCircleNN.py`'s pattern.
- **A fitness/accuracy-over-generations line plot was requested but not yet built.** Needs: (1) `trainingLoop` recording the best network's loss/accuracy every generation into a list (currently computed for the `tqdm` postfix each iteration but discarded, not retained), (2) a new plotting function (line plot, not heatmap — x = generation, y = accuracy/loss, one line per architecture) to compare e.g. `[2,2]` vs `[5]` vs `[3,3]` vs `[10]`'s learning curves directly.
